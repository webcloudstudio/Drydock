## Milestones

- **drydock diagnose** — reads a failed run, explains what stopped it, and proposes fixes to the
  specifications that allowed it.
- **DATABASE.md persistence layer** — the database moves behind a repository class, and the
  Blueprint names the calls instead of the schema.

## drydock diagnose

```text
drydock diagnose [<Target>]
```

A run fails and leaves logs. This reads them. It first prints where the project stands — INIT,
ANALYZE, PLAN, BUILD, or SCORE — and the recorded reason it stopped. That part is computed from
what Drydock already wrote down, so it is free and it prints even with no provider reachable. It
then makes one LLM call and writes the failure up as an incident report, in Markdown to paste into
a ticket and HTML to read.

The useful half comes after. Most failures are not typos in the code; they are gaps in what the
Commander asked for. So the diagnosis proposes edits to the specifications that allowed the failure
— the Compass files and the Manifest — as diffs. Drydock verifies each diff applies before showing
it, then asks about them one at a time. A declined amendment is recorded as a recommendation rather
than lost. `--apply` takes them all; a non-interactive run takes none.

## DATABASE.md persistence layer

Application code no longer touches the database. It calls repository methods that take and return
plain objects, while SQLAlchemy models, sessions, and SQL stay inside the persistence module, and
schema changes are Alembic revisions rather than something startup does. `DATABASE.md` now names
those calls — one id per call, with its inputs and outputs — and a feature cites the call, not the
table. That is what makes a migration safe to reason about: change a column behind a stable call
and nothing downstream rebuilds; change the call and Drydock knows who is affected. A Python target
with a database must select SQLAlchemy and Alembic — QuarterDeck will not approve the stack without
them, and `drydock plan` stops rather than author a Blueprint against the wrong shape.

One limit: a change is classified `unchanged`, `data`, or `rebuild`, but only `rebuild` currently
selects consumers. Grading it finer means letting each consumer declare what it is sensitive to,
which the Manifest does not yet model.
