## Milestones

- **drydock diagnose** — reads a failed run, explains what stopped it, and proposes fixes to the
  specifications that allowed it.
- **DATABASE.md persistence layer** — the database moves behind a repository class, and the
  Blueprint names the calls instead of the schema.

## drydock diagnose

```text
drydock diagnose                        — the latest run of the current Target
drydock diagnose <Target>               — the latest run of one Target
drydock diagnose <Target> --run <stamp> — an earlier run
drydock diagnose <Target> --apply       — apply every verified amendment
drydock diagnose <Target> --no-apply    — record them as decisions, change nothing
```

**Diagnoses the last run and identifies the root cause.** Where the project stands and the
recorded reason it stopped print first and cost nothing.

`drydock diagnose` then calls the LLM to write a structured report detailing the root cause,
providing evidence, next steps, and a proposed set of diffs to the input specifications that
remediate the issue. A Blockers and Decisions section states what the Commander must answer
before the run can proceed.

A stopped run is an opportunity, not a failure. It is rarely a broken specification; it is an
under-specified one, and the remedy is an edit to the specification plus specific remediation
instructions. Printing the proposed diff is what makes that remedy concrete — the exact line, in
the named file, verified to apply, approved one at a time.

## DATABASE.md persistence layer

**The persistence layer exists to keep application change out of the database and database change
out of the application.** Without that invariant every schema edit reaches every feature that
reads it, and the whole system rebuilds.

Application code no longer touches the database. Every SQL call goes through SQLAlchemy, behind
repository methods that take and return plain objects, and Alembic version-controls every schema
change in a release. `DATABASE.md` names those calls — one id each, with inputs and outputs — and
a feature cites the call, not the table.

Change is then classified rather than assumed. A change behind a stable call invalidates nothing.
A change to the call invalidates the downstream Blueprints that consume it, and those are forced
to rebuild; service consumers rebuild according to the service mapping and the type of change.

Every persistence change lives in Alembic. `drydock refit` reads the specification diff since the
commit it last consumed — Drydock records that commit at each step — and routes a schema change
into one `DATABASE.md` story whose implementation is an Alembic revision.

One limit: a change is classified `unchanged`, `data`, or `rebuild`, but only `rebuild` selects
consumers today. Finer grading needs per-consumer sensitivity, which the Manifest does not model.
