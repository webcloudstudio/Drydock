## Milestones

- **drydock diagnose** — a self-diagnostic command that explains why a Target's latest run stopped
  and proposes durable corrections to the governed inputs that allowed it.
- **DATABASE.md persistence layer** — persistence becomes a project-owned class library with a
  named contract per call, and the Blueprint states that contract instead of a schema.

## drydock diagnose

```text
drydock diagnose [<Target>] [--run <stamp>] [--apply] [--no-apply]
```

A failed run leaves plenty of evidence and no account of itself. The operator has a stack trace, a
log directory, and a workflow state file, and the work of turning those into "the plan step stopped
because the acceptance container would not parse, and here is the Compass line that let it happen"
is the work `drydock diagnose` does. The command is three things in a fixed order, and the order is
the design.

It first prints what Drydock already knows, before spending anything. The milestone ladder — INIT,
ANALYZE, PLAN, BUILD, SCORE — is computed from `PROJECT_STATUS.jsonl`, and the failure
classification is read from the stop `build_run` already recorded. A run halted by a provider rate
limit says so deterministically. The model is never asked to identify a fact Drydock wrote down,
which is also why this half of the report costs nothing and prints even when no provider is
reachable.

The ladder reports at milestone granularity because that is the lifecycle an operator thinks in,
and because it is what makes supersession correct. Supersession is named explicitly in
`project_status.SUPERSEDES` rather than inferred from position: a passing `PLAN REPAIRED` retires a
failed `PLAN CREATED`, and a passing `BUILT` retires a failed `BUILDING`. A passing `SCORE BUILD`
deliberately does not retire a failed `SCORE AC`, because the build report is observational and
reports on different work than the acceptance gate. A milestone failure that was never answered
remains the lifecycle frontier however far the project later advanced.

It then makes exactly one model call. The bundle behind that call has to be repair-grade — a reader
who never saw the run must be able to fix the defect from the report alone — so it carries the
failing text, the criteria that disagreed, the governed inputs a correction would amend, and the
local path of every stream worth opening next, each with a SHA-256 digest drawn from
`logs/llm.jsonl` and `logs/history.jsonl`. It also has to fit in a prompt, so every excerpt is
line-bounded and states its bounds; the model never presents a truncated file as a whole one.

The model writes section prose and the module writes the file. That split is what lets the report
keep a deterministic header, ladder, and evidence table regardless of what came back, and it is why
a malformed answer still produces a readable document, marked `MALFORMED`, with the raw text
preserved rather than nothing at all.

It then asks the operator, one amendment at a time. Amendments are unified diffs against
`COMPASS.md`, `PLAN_COMPASS.md`, `ANALYZE_COMPASS.md`, or `MANIFEST.md`, and every one is applied
to an in-memory copy of the current file before the operator sees it; a diff that will not apply is
reported as unapplicable instead of offered. Approval is per amendment, because a diagnosis
proposing three corrections asks three questions and an operator who agrees with two should not
have to refuse all three to decline the third. `--apply` applies all without prompting; `--no-apply`
and any non-interactive session record them as `recommended` decisions in `DECISIONS.json`, so a
declined correction survives the session instead of scrolling away.

The diagnosis is written twice into the Target root beside `SCORECARD.md`. `DIAGNOSE_<stamp>.md` is
what an operator pastes into a ticket or hands to another agent, and `DIAGNOSE_<stamp>.html` is what
they read; the page shares `report_render` with `drydock score report`, so the two documents carry
the same letterhead, verdict stamp, and tab strip and are recognisably one family. They stay
separate artifacts all the same: a receipt proves what a run delivered, a diagnosis explains why one
stopped. Every exit names the next command to run.

## DATABASE.md persistence layer

Persistence in Drydock has always been a boundary rule rather than a schema rule: every persistent
store and external service is reached through a typed class the project owns, and a code review
that finds raw SQL, `os.environ`, `open()` on application data, or a cloud SDK import outside its
encapsulation class fails. That rule generalizes across store types — a relational store gets a
repository, configuration gets a typed `Config` class, a directory gets a `FileStore`, an external
service gets a wrapper — so the application is written against a class library it owns rather than
against four vendors' APIs.

The rule had one exception, and the exception defeated it. Where an ORM was used, `persistence.md`
V1 treated the ORM model class as the table encapsulation and forbade a second hand-written layer.
But an ORM model is a storage internal with lazy loading, session affinity, and a live identity map
attached to it; handing one to a route publishes the schema as the application interface. Once the
schema is the interface, every column rename is a consumer-visible change, and nothing can size the
blast radius of a migration because there is no smaller contract to compare against.

V2 withdraws the exception. SQLAlchemy models and sessions are private to `persistence/`, a
project-owned repository returning DTOs is the application boundary, and the path is fixed:

```text
route → service → repository → SQLAlchemy session/model → database
```

Routes and services never receive an ORM model, `Session`, `Row`, SQL string, table name, or column
name. The application owns the configured `sessionmaker`, each unit of work opens one session and
commits or rolls back at its edge, and repository methods never commit independently.

The Blueprint changes with it, which is the part that matters to planning. `DATABASE.md` is the
project's persistence contract, not its SQL schema: every access pattern now carries a stable
`DATA-<DOMAIN>-<NNN>` id, the repository method that serves it, its DTO input and output shapes,
its consumers, and a compatibility level. Route and screen Blueprints cite those ids and the fields
they render or accept, and cite nothing physical — no table, column, ORM model, session, or SQL
statement. A schema change that leaves the named call contract intact therefore invalidates no
downstream Blueprint, and one that breaks a call names exactly who is affected.

Schema history moves to Alembic. Revisions in `migrations/versions/` are the source of truth,
production and development advance only through `alembic upgrade head`, and application startup
does not alter schema — `Base.metadata.create_all()` survives only in disposable tests.
Autogenerated revisions are drafts: every operation, backfill, index, constraint name, upgrade, and
downgrade is reviewed before commit, and verification means upgrading an empty database to head,
upgrading a database at the prior revision to head including its backfill, and running the
repository contract tests after each.

None of that holds unless the stack says so, so the requirement is enforced where a Target can
still act on it rather than where it is expensive to fix.

| Enforcement point | Behavior |
|---|---|
| `technology_stack.required_rigging` | A declared Python technology plus `blueprint/DATABASE.md` makes `sqlalchemy.md` and `alembic.md` required |
| `technology_stack.approve` | Refuses to record approval while a required selection is absent |
| `technology_stack.is_approved` | Reports not approved, so QuarterDeck keeps the stack an outstanding action |
| `planning_session.create_plan` | Raises before authoring, naming the missing selections and where to set them |

Planning is the right gate. The boundary decides how every story is written — which module owns the
session, what a service receives, what an acceptance criterion may assert — so a Target that
discovers the rule at build time rewrites its Blueprint, not its code. A running QuarterDeck picks
up the enforcement on restart: `drydock run quarterdeck <Target>`.

The governed inputs move together, because a rule that only the gate knows is a rule builders
rediscover by failing. `analyze.md` emits `Python`, `SQLAlchemy`, and `Alembic` rows for a Python
product that persists relational data and identifies the `DATA-<DOMAIN>-<NNN>` contracts while it
still has the sources in hand. `BLUEPRINTS_CONTRACT.md` states the repository boundary as the
`DATABASE.md` scope rule. `Rigging/spec_template/DATABASE.md` ships the new table shapes.
`postgres.md` and `sqlite.md` keep their driver examples but mark them background: they are no
longer patterns to copy into a Python relational application.

Refit follows the same contract. A source change that alters physical schema emits one `DATABASE.md`
story containing an Alembic revision, classified `unchanged` when every named input, output,
nullability, type, and behavior survives, `data` when an observable type or nullability changes, and
`rebuild` when a call is removed or renamed, an input becomes required, an output field disappears,
or semantics change. `lineage_route.validate_route` rejects anything else, and the prior spelling
`changed` parses as `rebuild` so lineage already recorded in a Target stays valid.

One honest limit: the three levels are a validated classification, not yet a graded rebuild. The
Manifest does not model per-consumer data sensitivity, so `source_refit` promotes only `rebuild`
into downstream impact and `data` is recorded but selects no consumer. Grading the rebuild means
letting consumers declare what they are sensitive to, which is a Manifest change and is not made
here. The classification lands first so that the lineage recorded today is the lineage that change
will read.
