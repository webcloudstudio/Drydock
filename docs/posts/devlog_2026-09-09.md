## Milestones

- **DATABASE.md persistence layer** — the database moves behind a repository class, and the
  Blueprint names the calls instead of the schema.

## drydock diagnose

```text
drydock diagnose                        — the latest run of the current Target
drydock diagnose <Target>               — the latest run of one Target
drydock diagnose <Target> --run <stamp> — an earlier run
drydock diagnose <Target> --apply       — apply every verified amendment
drydock diagnose <Target> --no-apply    — record them as decisions, change nothing
```

**Diagnoses the last run and identifies the root cause.**

`drydock diagnose` calls the LLM to write a structured report detailing

- Root Cause,
- Details
- Commander Feedback Requested
- Repair Pproposal ( diffs to input specifications )

Commander Feedback Reuested provides the next steps and may contain information collected from the system
BLOCKERS.md or DECISIONS.md

The Repair proposal methedology is effective because most every issue you encounter can be fixed by over specification
within the input material/blueprints.

## DATABASE Encapsulation

DATABASE.md has been modified to be fully encapsulate it to protect persistence changes from forcing downstream blueprint rebuild.  Encapsulation will prevent unneeded rebuilds.

New required packages **SqlAlchemy** and **Alembic**. These are provided by rigging for all systems requiring SQL database access.  SQLAlchemy encapsulates issues every SQL statement from Python objects; Alembic versions the schema as ordered migration scripts.

The use of **SqlAlchemy** enables call encapsulation to the database schema.  Blueprints use english names instead of queries and only know about that name and the input/output contract.  For example, a Blueprint named `FEATURE-ORDER.md` can call two persistence operations named `FEATURE-ORDER-001` and `FEATURE-ORDER-002`. `FEATURE-ORDER-001` might create an order. `FEATURE-ORDER-002` might retrieve an order by id.

To implement, `DATABASE.md` now has four new sections:

- `## Access Patterns` defines each named persistence operation. For example, `FEATURE-ORDER-001` calls `OrderRepository.create(CreateOrder) → Order`. It declares the Feature that uses the call, the operation, the input, the output, and its compatibility classification.

```markdown
### FEATURE-ORDER-001 — Create order

| Field | Value |
|---|---|
| Owner | FEATURE-ORDER.md |
| Access | write |
| Repository operation | OrderRepository.create(CreateOrder) -> Order |
| Compatibility | rebuild |

Input: CreateOrder

| Field | Type | Required |
|---|---|---|
| customer_id | UUID | yes |
| items | list[OrderItem] | yes |

Output: Order

| Field | Type |
|---|---|
| id | UUID |
| status | OrderStatus |
| total | Decimal |
| created_at | datetime |
```

- `## Persistence Interfaces` defines the application class that implements the call. For example, `OrderRepository` in `persistence/orders.py` implements the `FEATURE-ORDER-*` operations for `OrderService`.
- `## Schemas` defines the private database tables, columns, indexes, and relationships that `OrderRepository` uses.
- `## Migrations` defines the Alembic revisions that create or change that private schema.

To implement, each Blueprint can have an optional section named `## Database Interface`

```markdown
## Database Interface

- `FEATURE-ORDER-001` — write: create an order - supplies: `customer_id`, `items` - returns: `id`, `status`, `total`, `created_at`
- `FEATURE-ORDER-002` — read: retrieve an order by ID - supplies: `customer_id` - returns: `status`, `total`, `created_at`.
```

For this create-order example, the Feature supplies `customer_id` and `items` and receives `id`, `status`, `total`, and `created_at`.

`FEATURE-ORDER.md` cites `FEATURE-ORDER-001` and declares the input and output fields it uses. It does not name the database table, SQL statement, SQLAlchemy model, or Alembic revision. The builder implements route → service → repository → SQLAlchemy → database.

`drydock refit` has been modified to read the git logs to identify needed database changes and rewrite them as alembic logs. The alembic logs are then used to invalidate graph database nodes in the manifest downstream of the changed database call.  To mitigate this impact, Alembic database changes are classified `unchanged`, `data`, or `rebuild`.  Downstream  blueprints invalidated and forced to be rebuilt if they are "impacted" ( ie. they use the impacted calls ) AND the blueprint type is impacted by the classified change ( only `rebuild` is implemented ) AND the alembic change has not been implemented in a `drydock build`
