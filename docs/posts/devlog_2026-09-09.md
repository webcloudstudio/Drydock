This period delivers two threads. Drydock gains `drydock diagnose`, a self-diagnostic command that
explains why a Target's latest run stopped and proposes durable corrections to the governed inputs
that allowed it. Persistence gains a hard encapsulation boundary: a Python Target with a relational
`DATABASE.md` must select `sqlalchemy.md` and `alembic.md`, and the ORM exception that let an ORM
model serve as the application interface is withdrawn.

## Milestones

- **2026-08-30 — `drydock diagnose` ships.** Deterministic milestone ladder, one model call, a
  repair-grade incident report in Markdown and HTML, and confirmed amendments to `COMPASS.md`,
  `PLAN_COMPASS.md`, `ANALYZE_COMPASS.md`, or `MANIFEST.md`.
- **2026-09-09 — The persistence boundary becomes mandatory.** SQLAlchemy and Alembic Rigging are
  required selections for Python relational Targets, enforced at stack approval and again before
  planning authors a single Blueprint.

## The Persistence Boundary

`persistence.md` V1 carried an ORM exception: where an ORM was used, the ORM model class *was* the
table encapsulation, and a second hand-written layer was forbidden. The exception defeated the rule
it qualified. An ORM model is a storage internal with lazy loading, session affinity, and a live
identity map attached to it; handing one to a route publishes the schema as the application
interface. Once the schema is the interface, every column rename is a consumer-visible change and
Drydock has no way to size the blast radius of a migration.

V2 withdraws the exception. SQLAlchemy models are storage internals. A project-owned repository
returning DTOs is the required application boundary, and the governed path is fixed:

```text
route → service → repository → SQLAlchemy session/model → database
```

Only `persistence/` imports SQLAlchemy. Each public repository method corresponds to one
`DATA-<DOMAIN>-<NNN>` contract in `DATABASE.md`; its signature and DTO input and output are the
public persistence API. The application owns the `sessionmaker`, each unit of work opens one
session, and repository methods never commit independently. Schema advances only through
`alembic upgrade head`; application startup does not alter schema, and `Base.metadata.create_all()`
survives only in disposable tests.

The rule is enforced where a Target can still act on it, not where it is expensive to fix.

| Enforcement point | Behavior |
|---|---|
| `technology_stack.required_rigging` | A declared Python technology plus `blueprint/DATABASE.md` makes `sqlalchemy.md` and `alembic.md` required |
| `technology_stack.approve` | Refuses to record approval while a required selection is absent |
| `technology_stack.is_approved` | Reports not approved while a required selection is absent, so QuarterDeck keeps the stack an outstanding action |
| `planning_session.create_plan` | Raises before authoring, naming the missing selections and where to set them |

Planning is the correct gate. The boundary decides how every story is written — which module owns
the session, what a service receives, what an acceptance criterion may assert. A Target that
discovers the rule at build time rewrites its Blueprint, not its code.

## Migration Sensitivity

A schema change previously carried a binary `contract="changed"` flag on the routed story. The flag
forced a false choice. A revision that adds an index, or widens a column behind a stable repository
signature, invalidates nothing; declaring it changed rebuilds every consumer, and declaring it
unchanged is a lie the next build discovers. `drydock refit --sources` now classifies the change at
three levels, and consumers rebuild only at or above their declared sensitivity.

| Level | Meaning |
|---|---|
| `unchanged` | Physically visible only. Repository input, output, type, nullability, and behavior stay stable. |
| `data` | An observable repository input or output type, or a nullability, changes. |
| `rebuild` | A call is removed or renamed, an input becomes required, an output field is removed, or semantics change. |

`lineage_route.validate_route` rejects any other level. The prior spelling `changed` parses as
`rebuild`, so lineage already recorded in a Target remains valid.

## Self-Diagnosis

```text
drydock diagnose [<Target>] [--run <stamp>] [--apply] [--no-apply]
```

The command is three things in a fixed order, and the order is the design.

**It prints what Drydock already knows, before spending anything.** The milestone ladder — INIT,
ANALYZE, PLAN, BUILD, SCORE — is computed from `PROJECT_STATUS.jsonl`, and the failure
classification is read from the stop `build_run` already recorded. A run halted by a provider rate
limit says so deterministically. The model is never asked to identify a fact Drydock wrote down.

The ladder reports at milestone granularity because that is the lifecycle an operator thinks in,
and because it is what makes supersession correct. Supersession is named explicitly in
`project_status.SUPERSEDES` rather than inferred from ladder position: a passing `PLAN REPAIRED`
retires a failed `PLAN CREATED`, and a passing `BUILT` retires a failed `BUILDING`. A passing
`SCORE BUILD` deliberately does not retire a failed `SCORE AC` — the build report is observational
and reports on different work than the acceptance gate. An unanswered milestone failure remains the
lifecycle frontier however far the project later advanced.

**It then makes exactly one model call.** The evidence bundle must be repair-grade: a reader who
never saw the run must be able to fix the defect from the report alone. That rules out a bundle of
conclusions, so the bundle carries the failing text, the criteria that disagreed, the governed
inputs a correction would amend, and the local paths of every stream worth opening next. It must
also fit in a prompt, so every excerpt is line-bounded and states its bounds — the model never
presents a truncated file as a whole one. Cited log paths carry SHA-256 digests drawn from
`logs/llm.jsonl` and `logs/history.jsonl`.

The model writes section prose; the module writes the file. That split is what lets the report keep
a deterministic header, ladder, and evidence table regardless of what came back, and it is why a
malformed answer still produces a readable document, marked `MALFORMED`, with the raw text
preserved.

**It then asks the operator, one amendment at a time.** Amendments are unified diffs against
`COMPASS.md`, `PLAN_COMPASS.md`, `ANALYZE_COMPASS.md`, or `MANIFEST.md`. Each is applied to an
in-memory copy of the current file before the operator sees anything; one that will not apply is
reported as unapplicable rather than offered. An amendment that fails to land after approval is
worse than no amendment, because trust in the whole report goes with it.

Approval is per amendment. A diagnosis proposing three corrections asks three questions: an
operator who agrees with two should not have to refuse all three to decline the third. `--apply`
applies all without prompting. `--no-apply`, and any non-interactive session, records them as
`recommended` decisions in `DECISIONS.json` so a declined correction survives the session instead
of scrolling away. Guessing a human's answer to "may I edit your Compass" is not a default this
command has.

The diagnosis is written twice, into the Target root beside `SCORECARD.md`.
`DIAGNOSE_<stamp>.md` is what an operator pastes into a ticket or hands to another agent;
`DIAGNOSE_<stamp>.html` is what they read. The page shares `report_render` with
`drydock score report` — the same letterhead, verdict stamp, tab strip, and table styling — so the
two documents are recognisably one family. It remains a separate artifact: a receipt proves what a
run delivered, a diagnosis explains why one stopped. Every exit names the next command to run.

## Changes

- **2026-08-22 — Fused acceptance boundaries repaired deterministically.** Two criteria emitted
  under one `=== AC <id> ===` opener are now repaired at plan-generation time and by
  `drydock plan repair` with no model call, because the LLM container repair failed identically on
  every retry.
- **2026-08-23 — `drydock score build` becomes observational.** Missing evidence stays visible but
  no longer fails the exit code, alters `PROJECT_STATUS.jsonl`, or rewrites `SCORECARD.md`;
  `score ac` and `score release` remain the acceptance and release gates.
- **2026-08-23 — `helpers/diagnose.sh` and `helpers/diagnose-uat.sh` added.** Bounded, read-only
  adversarial diagnosis of the latest failed run, run against two providers independently.
- **2026-08-30 — `drydock diagnose` added.** A deterministic account of where a run stands, one
  model call, a repair-grade report in two surfaces, and confirmed amendments to the governed
  inputs.
- **2026-08-30 — Project state resolved by milestone.** Explicit supersession in
  `project_status.SUPERSEDES` stops `drydock status`, `drydock score report`, and
  `drydock diagnose` reporting a failure the project already recovered from.
- **2026-09-09 — SQLAlchemy and Alembic required for Python relational Targets.** QuarterDeck
  rejects stack approval and `drydock plan` blocks before authoring until both Rigging selections
  are present; `drydock refit --sources` classifies persistence changes `unchanged`, `data`, or
  `rebuild`.
