## Milestones

- **drydock diagnose** — reads a failed run, explains what stopped it, and proposes fixes to the
  specifications that allowed it.
- **DATABASE.md persistence layer** — the database moves behind a repository class, and the
  Blueprint names the calls instead of the schema.

## drydock diagnose

```text
drydock diagnose                        — the latest run of the current Target
drydock diagnose <Target>               — the latest run of one Target
drydock diagnose <Target> --run <stamp> — an earlier run
drydock diagnose <Target> --apply       — apply every verified amendment
drydock diagnose <Target> --no-apply    — record them as decisions, change nothing
```

Diagnoses the last run and identifies the root cause. Where the project stands and the recorded
reason it stopped print first and cost nothing. One LLM call then writes a structured report —
root cause, evidence, next command — as Markdown and HTML in the Target directory.

It also proposes the fix. Most failures are gaps in what was specified, so the report carries
diffs against the Compass files and the Manifest, each verified to apply and confirmed one at a
time.

## DATABASE.md persistence layer

Application code no longer touches the database. It calls repository methods that take and return
plain objects; SQLAlchemy models, sessions, and SQL stay inside the persistence module, and schema
changes are Alembic revisions. `DATABASE.md` names those calls — one id each, with inputs and
outputs — and a feature cites the call, not the table. Change a column behind a stable call and
nothing downstream rebuilds; change the call and Drydock knows who is affected. A Python target
with a database must select SQLAlchemy and Alembic: QuarterDeck will not approve the stack without
them, and `drydock plan` stops rather than author against the wrong shape.

One limit: a change is classified `unchanged`, `data`, or `rebuild`, but only `rebuild` selects
consumers today. Finer grading needs per-consumer sensitivity, which the Manifest does not model.
