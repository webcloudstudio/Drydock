## Which To Use

| Situation | Use |
|---|---|
| One-file fix or exploratory hacking | Plain CLAUDE.md |
| Nothing written down yet | BMAD-METHOD |
| Free, agent-neutral team convention | GitHub Spec Kit |
| IDE-centric team, spec-first with editor hooks | Kiro |
| Large system, spec already written, months of work | Drydock |
| Delivery that must be audited or defended | Drydock |
| Long-lived product whose spec keeps changing | Drydock |
| Maximum agent throughput on independent work | None of these |

The natural pairing is BMAD or Kiro upstream, Drydock downstream.

## The Wider Field

Eleven systems on the same scale. Maturity follows Böckeler's taxonomy: **spec-first** (the spec guides the first build, then drifts), **spec-anchored** (spec and code co-evolve under tests), **spec-as-source** (humans edit only specs).

## Where Drydock Must Improve

1. **Right-sizing.** No lightweight path. A one-line change pays the full pipeline.
2. **Parallel execution.** Scores zero while owning the dependency graph that makes it safe.
3. **Authoring.** A deliberate non-goal, but it means Drydock cannot be a team's only tool.
4. **Stack coverage.** Python Rigging only. Every other team writes governance before evaluating.
5. **Proof locking.** Criteria are gated but not hash-locked before implementation.
6. **CI gate.** The release verdict is not packaged as an exit code a pipeline can enforce.
